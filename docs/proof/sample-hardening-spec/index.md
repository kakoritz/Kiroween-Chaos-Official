# Sample hardening spec (TV3-C9, C11, C12, C13)

Generated by the pattern miner and spec writer from a real run, not typed by hand. The run id in the spec files is `imp-mwrx7spi`; the real folder name was `.kiro/specs/hardening-imp-mwrx7spi/`.

## How it was made

1. `npm run build:bots`, then `HAUNT_PORT=7081 HAUNT_PROVIDER_PORT=7082 npm run demo -- --no-open` (the live server with real bots, fresh `.haunt`).
2. `npm run haunt -- improve --url http://127.0.0.1:7081 --seed 7 --speed 4 --pace show --rounds '[{"lanes":5,"orders":5,"intensity":5},{"lanes":4,"orders":5,"intensity":5}]'`: run the tournament (lessons reset), mine, apply the cheap patterns as policy overlay, write the spec for the rest, rerun the same plan and seed, compare.
3. `npm run haunt -- spec-lint .kiro/specs/hardening-imp-mwrx7spi` answered `spec-lint ok (6 requirements)`.

## Files

- `requirements.md`, `design.md`, `tasks.md`, `README.md`: the spec (EARS requirement with evidence, impact and hypothesis; the smallest patch with a diff budget, risk and rollback; tasks with a regression test and an acceptance line; sorted by downtime cost).
- `improve-report.txt` and `improve-report.json`: what the loop printed, and the same numbers as data.
- `patterns.json`: the pattern store entries of this run (evidence trimmed).

## The result, with the real numbers

**Closed 5 of 9 patterns, and 2 more on every lane that took a policy. Grade C before, B after. Reliability 70 to 87, lost orders 9 to 2, round points 1379 to 4959.**

The previous proof of this folder was closed 0 of 5, grade C before and after. Why, and what changed in the engine:

- A lesson was taught by one fault (`http_404`) and matched only that status, but the same stage fails as a 429, 500 or 522 in the next round. A rule now answers any transient failure of its stage.
- Only `retry_backoff` did anything. `idempotency_key`, `journal_replay` and `breaker_park` are now levers the SDK obeys (a derived key, one replay from the journal after a cool-down, a breaker that trips after two failures so the order parks). The transit poll and the handoff retry read the overlay as well.
- A false "swallowed" classification of cursed answers (the ledger's effect events reach the log before the bot's `order_start`) put phantom patterns in the first run; they are gone.

What stays open, and why it is honest:

- `payment + http_404 + order_lost` is gone from lanes 2, 3 and 4 (the ones that took the backoff lesson). The Rookie (lane 1) has no `retry` part, still loses it, and so the pattern is not verified. That is the code change in the spec.
- `payment + http_404 + retry_storm`, `payment + endpoint_failure_rate + degraded` and `account + slow_link + outage` describe the injected storm, not a bot reaction. Backoff makes more attempts, not fewer, so they do not close.
- The first run's round 1 already teaches lessons that apply in its round 2 and in the rerun (reported as `existing`). The "before" numbers include them. Runs are not byte-identical (wall-clock scheduling), so a run may show a pattern or two that the other did not (`newPatterns`).

Nothing in this folder was applied to code. Kiro applies a spec with the review step.
