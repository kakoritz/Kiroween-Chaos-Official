# Share, adopt, prove (requirements and design)

Goal: make Haunt something a developer **adopts** (badge, CI gate, try-your-own-workflow) and make the **Kiro usage visibly deep and honest** (live fix, traceability, MCP scene, installed Power and Crew app). These target Potential Impact, Technological Implementation and Innovation, and remove the judge-panel red flags about "recorded" proof.

## 1. Requirements (EARS)

1. THE CLI SHALL generate a **grade badge** (SVG) and a **scorecard** (SVG and HTML, 1200x630 social card) from a run. (SH-C1)
2. THE REPO SHALL ship a reusable **GitHub Action** that runs `haunt sweep`, uploads the report, comments the grade on the pull request and fails when targets fail. (SH-C2)
3. THE hosted demo SHALL include a **Workflow Lab** where a visitor models their own workflow and gets a graded report and fixes. (SH-U1, SH-C3)
4. THE loop proof SHALL be **real**: the reviewer writes a hardening spec and **Kiro applies it live**, and the wave 2 grade is verified. Recorded fixes SHALL be labelled "recorded". (SH-C4)
5. THE REPO SHALL provide a generated **traceability table** from requirement and task IDs to pull requests and tests, regenerated by a hook. (SH-K1)
6. THE REPO SHALL provide a single **Kiro write-up** in the rubric's order, with candid notes of what Kiro did well and badly. (SH-K2)
7. THE Kiro Power and the Kiro Crew app SHALL be **installed and shown working** with screenshots. (SH-K3)
8. THE repo SHALL include an **MCP demo scene** script: a Kiro agent calls `haunt_sweep` on a new workflow, reads the matrix and patches the code. (SH-K4)
9. THE reviewer SHALL offer an optional **LLM mode** (Kiro CLI or API key) with the rule-based reviewer as fallback, and a hook SHALL trigger it at wave end. (SH-C5)
10. THE hosted demo and the CLI SHALL show an **architecture diagram**. (SH-D1)

## 2. Badge and scorecard (SH-C1)

- `haunt badge <run-id> [--out dir]` writes `haunt-badge.svg` (shields style, 20 px tall: label "Haunt", value "A 94", colour by grade: A green, B lime, C amber, D orange, F red) and `haunt-scorecard.svg` plus `haunt-scorecard.html`.
- **Scorecard content** (1200x630): title "Haunt resilience scorecard", app name, big grade ring and score, reliability %, repeats, lost orders, recovery p50 and p95, a mini **coverage heat-map** (stage by fault, six colours), the tier comparison bars if present, three worst findings in one line each, footer "tested with Haunt · kakoritz/Kiroween-Chaos". Pure code, no external fonts or images, deterministic.
- MCP tool `haunt_badge`, and an arena **"Share" button** in the report viewer that downloads the SVG and copies the README snippet `![Haunt grade](./haunt-badge.svg)`.
- The scorecard is the asset for the Social Blitz post and the Devpost gallery.

## 3. GitHub Action (SH-C2)

- `.github/actions/haunt-sweep/action.yml` (composite): inputs `config` (path to `haunt.yaml`), `tiers`, `fail-on` (targets|never), `comment` (true|false). Steps: set up Node, install, run `haunt sweep --config ... --out .haunt/out`, upload `report.html`, `report.json` and the badge as artifacts, post or update a PR comment with the Markdown report and the badge (using `gh`), exit non-zero if targets failed.
- `docs/examples/haunt-ci.yml` shows usage. A **demo repository** (`kakoritz/haunt-demo-action`, optional) has a deliberately fragile workflow and a PR that goes from red to green.
- **Policy note:** the owner decided earlier that CI does not run the project's own test suite. This Action runs the product's sweep on a user's workflow, which is different. Keep it as an **opt-in example workflow and a published Action**, not a required check on this repo, unless the owner decides otherwise (record in `docs/DECISIONS.md`).

## 4. Workflow Lab (SH-U1, SH-C3)

A page in the hosted demo for visitors who do not want to install anything. It is a **model-based what-if**, labelled honestly as such, and the path to the real tool is one click away.

1. **Describe:** a form to list stages (name, role: input, work, effect, poll, final) and, for each effect, its kind and whether a key is used; or paste a `haunt.yaml`. Presets: "Orders", "Inbox", "Payments", "Report generator".
2. **Choose protections:** toggle the five parts for the modelled process (retry, journal, idempotency, breaker, offline queue) or "none (my bot today)".
3. **Run:** the browser engine runs a generic bot built from the declared stages and parts against the fault catalog (a sweep) and shows the arena animation plus the report: grade, coverage matrix, worst findings, **"add this part" suggestions** mapped from the reviewer rules R1 to R8.
4. **Export:** download the generated `haunt.yaml`, the badge and the scorecard; show the three commands to run the real sweep on real code (`npx haunt init`, `haunt validate`, `haunt sweep`).
Core builds the generic bot and the in-page sweep (SH-C3); UI builds the form, presets and results (SH-U1).

## 5. The real loop proof (SH-C4)

The judge panel flagged: the video promises "F to A" but the proof was F to C with a recorded fix.

- **Goal:** wave 2 shows grade **A** for the hardened lane on the loop demo, and the fix is applied **by Kiro, live, from the reviewer's spec**.
- **Procedure** (`docs/proof/live-fix.md`): run the loop's wave 1 (Rookie F), the reviewer writes `.kiro/specs/hardening-<run-id>/`, open the spec in Kiro (IDE, CLI or Crew), run its tasks, review the diff to `apps/haunted-orders/src/bots/rookie.ts`, rebuild bots, run wave 2. Save the transcript, the diff, both reports and a screen recording into `docs/proof/` with dates.
- **Making the A real:** the hardening spec must include every part the findings demand (retry, journal, idempotency, and for lost orders the breaker and offline queue if the matrix shows them). If a wave 2 A is not reachable with a crash-only plan, **say what the plan covers** ("crash at Payment on every order") and show the full sweep grade next to it, never a bigger claim than the evidence.
- **Honesty labels:** any asset that replays a recorded fix (the browser demo) carries a visible "Recorded fix" tag; the live fix is shown in the video with the real Kiro session.
- Acceptance: `docs/proof/` has the real run; wave 2 grade A on the plan stated; the video script claims exactly that.

## 6. Traceability (SH-K1) and write-up (SH-K2)

- `tools/trace.ts` scans `.kiro/specs/**` for requirement and task IDs (for example `R4.1`, `PT-C4`, `H1.2`, `P9`), `git log` for PR numbers in commit subjects (`(#123)`), and test files for `// covers: <ID>` comments. It writes `docs/TRACE.md`: ID, text (first 80 chars), task status, PR links, test files. A **hook** `.kiro/hooks/trace-on-merge` regenerates it when specs or tests change. Tests add `// covers:` lines as they are touched.
- `docs/KIRO-WRITEUP.md` follows the rubric order: IDE, CLI, Web and Crew (what each was best at), custom agents (`chaos-director`, `reviewer`), hooks (each with a measured benefit), spec-driven development (a real comparison to vibe coding on one feature, with numbers: tasks, tests, defects), steering (which file changed Kiro's behaviour and how), MCP (`haunt-mcp` and what it made possible), property-based testing (the bug it found, with the shrunk counterexample), Powers, and a **"what Kiro got wrong"** section. KIRO-LOG gets candid entries ("Kiro did X, I corrected Y") rather than PR bookkeeping. Five short quotes or moments become the Devpost text.
- Steering files to add: `tech.md` (stack and test rules), `contract.md` (the contract and PR rules), `art.md` (style guide pointers) so the steering surface is visible and used.

## 7. Power, Crew app, MCP scene, LLM reviewer (SH-K3, SH-K4, SH-C5)

- **Install proof:** install `kiro-power/` and `kiro-crew-app/` into a real Kiro and Kiro Crew; capture screenshots and a 20 s clip of each working; replace "not installed" notes; add to `docs/proof/installed/`.
- **MCP scene** (`docs/proof/mcp-scene.md`): in Kiro, an agent builds a small workflow (`apps/` sample or the Workflow Lab preset), calls `haunt_define` and `haunt_sweep`, reads the matrix and **patches the code**, calls `haunt_sweep` again, grade improves. Recorded for the video (20 s).
- **LLM reviewer:** `reviewer --llm` uses Kiro CLI (`kiro` headless) or `ANTHROPIC_API_KEY` to draft the hardening diff inside the spec; falls back to rules. A hook runs the reviewer when a wave ends.

## 8. Architecture diagram (SH-D1)

One diagram: browser UI, SSE and REST contract, runner, bot processes, provider and ledger, journal, adapters (SDK, Proxy, Process), reviewer, Kiro loop. Authored as mermaid in the README and exported as SVG in `docs/img/architecture.svg` (a Lucid board is optional). Shown in the video end card and the Devpost gallery.

## 9. Acceptance

1. `haunt badge` produces deterministic SVGs (same run, same bytes) and the Share button downloads them.
2. The Action runs on a sample repo: red then green across two PRs, with a PR comment each time.
3. The Workflow Lab produces a graded report for a modelled workflow in under 10 s in the browser and lets the visitor download `haunt.yaml`.
4. The real loop proof exists in `docs/proof/` with wave 2 grade A on the stated plan.
5. `docs/TRACE.md` regenerates by hook and maps at least 90 percent of requirement IDs to a PR and a test.
6. `docs/KIRO-WRITEUP.md` covers every Kiro item in the rubric and has a "what Kiro got wrong" section.
7. Power and Crew app screenshots exist and show them installed and working.
