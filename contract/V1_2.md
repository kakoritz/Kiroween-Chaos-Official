# Contract v1.2 (additive, `contractMinor: 2`)

Adds to `PROTOCOL.md`, `CONTRACT.md` and `V1_1.md`. `contractVersion` stays 1. Rules continue at 48. Source: `.kiro/specs/tournament-v3/spec.md`. Contract-label PR; Lane B approves.

## 1. Stage list is data
`state` and `hello` carry `app.stages`: `[{id, label, kind: "effect"|"read"|"poll"|"final", icon?}]`. The UI draws chips from this list.
- `orders` (v2 order): `account, create, submit, payment, confirmation, receive, process, updates, ship, transit, handoff`.
- Legacy runs (`intake, account, ...`) keep working: if `app.stages` is missing the UI uses the legacy list (rule 48).
- `stage` in events is one of `app.stages[].id`.
- Carrying (TV3-C1): `state.app` and `hello.app` stay the app id string, so v1.0 and v1.1 clients keep working (rule 48). The list itself is `state.stages` and `hello.stages` (each item also keeps `icon` and `workAnimation`); a client reads `app.stages` when `app` is an object, else `stages`, else the legacy list. `GET /api/apps` items carry `stages` too.
- Legacy mapping for old recorded runs: `intake` becomes `create` (and `submit`), `dispatch` becomes `ship`, `tracking` becomes `transit` (`legacyStage()` in the shared catalog). The validator checks a stream that uses `intake` against the legacy list, and a stream whose `hello` carries `stages` against that list.
- New effect kinds in `effect` and `repeat` events: `order` (stage `submit`, key `<order>:order`) and `store` (stages `receive` and `process`, keys `<order>:store:1` and `<order>:store:2`). `ship` keeps kind `dispatch`; the ledger columns are ACCOUNTS, ORDERS, CHARGES, RECEIPTS (email), STORE, SHIPMENTS, NOTICES.

## 2. Rounds and the review state

- `POST /api/next` resumes after `awaiting_next`; `GET /api/tournament` returns rounds, standings, corpses, awards, casebook.
- Rule 49: after `round_end` or `wave_end` in a tournament or campaign the server emits `awaiting_next` and starts no orders until `POST /api/next` (or an explicit `autoContinueSec` setting).
- Rule 50: eliminated lanes emit no further order events but remain in `state.lanes[].fallen = {round, stage, cause}`.

### Implementation notes (TV3-C7 tournament)
- `POST /api/tournament/start {lanes?: 2..5, rounds?: [{lanes, orders, intensity}], seed?, speed?, pace?}` starts round 1 at once (409 `wave_running` if a wave runs, 400 on bad input). Default rounds: 5, 4, 3, 2 lanes, 6, 8, 10, 12 orders, intensity 3, 5, 7, 9. Lane n always runs tier n (Rookie to Phoenix), so a corpse keeps its place. One round is one wave (wave n is round n). `POST /api/next` starts the next round (409 `not_awaiting_next` otherwise). `GET /api/tournament` answers `{seed, phase: running|awaiting_next|done, round, total, rounds, alive, standings, history[], corpses[], fallen, cumulative[], champion?, wave}` or `{phase: "idle"}`.
- Order of events of a round: `wave_start`, `lane_ready` for the live lanes, `intensity {source: "plan"}`, `round_start {round, total, lanes[], orders, intensity, seed}`, the wave, `wave_end`, `round_end`, then `corpse {kind: "wall"}` for each wall, then per eliminated lane `lane_eliminated` and `corpse {kind: "eliminated"}`, then `awaiting_next {round, next}` (or `tournament_end {champion, tier, rounds, awards[], casebookRef}` after the last round). Rule 49 holds: after `awaiting_next` no `order_start` or `stage_start` until the next `wave_start`.
- `round_end.detail`: `{round, total, standings[{lane, tier, rp, cumRp, rank, ok, lost, repeats, abandoned, downtimeMs, avgStars, issues, lessonsBonus, halted?, eliminated?}], eliminated?, eliminatedLanes?, rule, lessons[], cases[], awards?, casebook?}`. `rank` is by cumulative RP (1 is best). RP = ok x 100 - lost x 300 - repeats x 150 - abandoned x 150 - downtime penalty + review points + lessons bonus (cap +200). Lowest cumulative RP drops; ties: more lost, more repeats, lower average stars, higher downtime, lower lane number. A halted lane (`lane_halted`, or every order failed) drops at once.
- A wall is every one of a lane's orders failing an attempt at the same stage in the round; the lane may survive. Rules 57 to 61 (validator): 57 `round_start` and `round_end` agree on the round and the live lanes, 58 standings and ranks, 59 eliminated lanes, corpses and rule 50 (a fallen lane emits no `order_start`, `stage_start` or `order_done`), 60 rule 49, 61 the champion never fell.
- `state.corpses[]`, `state.lanes[].fallen {round, stage, cause}`, `state.awaitingNext` and `state.tournament {round, total, phase, alive, champion?}` are rebuilt from the events, so a late page sees them (rule 51). Round 1 starts a clean board: fallen lanes stay (greyed) until the tournament ends.
- The storm: one seeded plan per round (`roundPlan(seed, round)`), the same presses at the same orders and stages for every live lane, windows drawn once so every lane gets the same length. The wave seed is the same for all lanes of a round, so they get the same orders. Chaos mode is `manual` during a tournament (the plan is the storm); the floor rule still adds a gremlin to a lane with no issue.
- Fixtures: `tournament-r1-r4`, `elimination-corpse` (two rounds), `wall-corpse` (a Retrier that stumbles at Payment on every order, plus the Rookie dropped), `awaiting-next` (round 1 ends and waits). The mock server plays them: `POST /api/tournament/start` plays round 1 and waits, `POST /api/next` plays the next round.

### Implementation notes (TV3-C8 lessons)
- `lesson {lane, signature, mechanism, round, via: "overcame"|"suggested", action?}` (stage on the envelope) is a lane event emitted right after `round_end`, before `lane_eliminated`. Rule 62: the signature is `stage + fault + consequence`, `via` is one of the two words, the lane was live in the round. `round_end.lessons[]` lists the same lessons (`{lane, signature, stage, fault, mechanism, action?, via, learnedRound, applied}`) and, for losses the tier cannot fix with its parts, spec suggestions (`{lane, suggestion: true, signature, action, part, rule, round}`).
- Learning (at round end, per live lane): a case the lane overcame (recovered, no repeat, a mechanism used) is a lesson (`overcame`) and earns +25 the first time that signature is overcome (cap +200 per round in RP, `standings[].lessonsBonus`). A lost or partly solved case takes the reviewer rule's proposal (R1 repeated effect -> idempotency key, R2 transient error ended the order -> retry with backoff, R3 and R4 -> breaker and queue, R7 crash -> journal replay): a lesson (`suggested`) if the tier's parts allow the action, else a spec suggestion. Actions by tier: Rookie none, Retrier `retry_backoff`, Journaler adds `journal_replay`, Reconciler adds `idempotency_key`, Phoenix adds `breaker_park` and `hold_and_reroute`.
- Policy overlay (`haunt.policy`): `{version: 1, rules: [{stage, fault, action, backoff?: "exp", maxAttempts?, key?: "order-id"}]}`. The server writes `<lessonsDir>/lane-<n>.policy.json` for every live lane when a round starts and the runner passes its path to the bot as `HAUNT_POLICY`; the bot SDK reads it at start. Only `retry_backoff` changes SDK behavior today: for the named stage and fault a bot with the `retry` part and no breaker retries with exponential backoff (500 ms doubling, 5 attempts) instead of 3 plain retries. The other actions are recorded and shown, their behavior is already the tier's own (a Reconciler already sends keys). Lessons persist in `<lessonsDir>/<lane>.json` (default `.haunt/lessons`), carry into the next round and the next tournament, and are cleared by `DELETE /api/lessons` or `resetLessons: true` on `POST /api/tournament/start`. `GET /api/lessons/:lane` answers `{lane, tier, lessons[], suggestions[], overcame[], policy}` (400 `bad_lane` outside 1 to 5).
- The mock server rebuilds lessons from `lesson` events (`GET /api/lessons/:lane`, `DELETE /api/lessons`); the tournament fixtures carry them.

### Implementation notes (TV3-C10 Casebook and awards)
- `case {signature, lane, round, order, outcome: "solved"|"partly"|"lost", mechanism?, costMs, costPoints, count, unknown?, fingerprint?}` (stage on the envelope) is a lane event, one per lane and signature per round (the first time the lane met it, with a `count`), emitted after the `lesson` events. Rule 63: signature `stage + fault + consequence`, a valid outcome, the lane was live. A signature is the stage where the fault landed (a deferred fault counts where it landed), the fault (a gremlin counts as its variant, an unknown fault as its base with `unknown`), and the consequence: `absorbed`, `recovered`, `duplicate_effect`, `order_lost`, `order_parked`, `order_quarantined`, `order_degraded`, `lane_halted`. Outcome: `solved` (done, nothing repeated), `partly` (done but repeated, parked or degraded), `lost`. Mechanism: `retry`, `retry_backoff`, `journal_replay`, `idempotency_key`, `breaker`, `queue`, `restart`, `absorbed`.
- Casebook lanes (after the UI review): `lanes[]` is one object per lane that met the case, in lane order. `outcome` is what the lane's cases add up to: `solved` (a real mechanism recovered it every time), `absorbed` (no recovery was needed, the fault did not matter; `mechanism: "absorbed"`), `lost` (every case lost), `partly` (anything mixed or partly handled). Absorbed is not solved: a row is `solved` only if some lane really solved it, `absorbed` when the only lanes that met it needed no recovery, and an absorbed lane is not in `solvedBy`, not a Battle-Tested count and not a lesson. Fastest Recovery ignores lanes with no recovery and recoveries of 0 ms.
- Casebook (`GET /api/casebook`, `round_end.casebook`, `tournament_end.casebook`): `{rounds, cases[], open[], note}`; a row is `{signature, stage, fault, consequence, firstSeen {round, order, lane}, lanes[{lane, outcome: "solved"|"partly"|"lost"|"absorbed", mechanism?}], solvedBy[{lane, tier, mechanism, round}], outcomes {solved, partly, lost}, met, cost {downtimeMs, points}, status: "solved"|"open"|"absorbed", recommendedFix {action?, part, rule?, mechanism?}|null, unknown?, fingerprint?}`. Open (nobody solved it) rows come first; their fix is the reviewer rule's proposal (R1 idempotency, R2 retry, R3 and R4 queue, R7 journal), a solved row's fix is the part its solvers used. The Casebook is always produced: with no cases it is `{cases: [], open: [], note: "No edge cases this time..."}`. `GET /api/casebook` also carries `awards`.
- Awards (`round_end.awards` as of that round, `tournament_end.awards` final): `[{id: champion|battle_tested|iron_skeleton|fastest_recovery|wooden_spoon, label, lane, tier, value?, text}]`. Champion exists only at the end; Battle-Tested is the lane with most distinct signatures solved; Iron Skeleton the fewest repeats (ties: higher RP); Fastest Recovery the lowest median recovery time; Wooden Spoon the first lane eliminated, worded kindly.

### Implementation notes (TV3-C11 pattern miner)
- Store: `.haunt/patterns.json` (`{version: 1, patterns[]}`), accumulated across runs and rounds; the same run key is never counted twice. A pattern is `{id: "p-<hash of signature>", signature, stage, fault, consequence, shapes[], count, lanes[], downtimeMsTotal, lostOrders, repeats, points, firstSeen {run, round?, order?, lane?}, lastSeen, status, runs[], evidence[{run, round?, seq[], journal[], report?}], solvedBy[{lane, mechanism}], unknown?, fingerprint?}`. Status flow: `new` -> `suggested` (a spec was written) -> `accepted` (a policy overlay was applied) -> `applied` (rerun with the change) -> `verified` (the rerun shows it gone) or `rejected`; a verified pattern that comes back is `new` again.
- The miner runs at every tournament round end (after `case` events). It reads the events (ledger rows as `repeat` and `effect`, laps, `outage`, `curse_response` when present), the Casebook cases and the lane journals (`path:line` evidence). Occurrences that hurt are counted (partly or lost cases); solved cases only fill `solvedBy`. Shapes: `case`, `hang` (a stage stuck longer than its p95 and 3x its median, at least 8 samples), `retry_storm` (3 failed attempts at one stage of one order), `failure_rate` (failed attempts at a stage over its starts, 30 percent or more), `curse` (swallowed or crashed answers), `outage` (the windows lanes sat through).
- Qualifies for a fix spec: count of 3, or any lost order, or more than 30 s of downtime.
- `pattern {id, signature, count, downtimeMsTotal, status, lostOrders, repeats, lanes[], qualifies, change: new|updated|regressed, unknown?, fingerprint?}` is a global event, emitted for each qualifying pattern that changed, after the `case` events of the round. Rule 64: id and signature present, status one of the six, count and downtime numbers. `spec_written {runId, path, patterns[], refused?, lint?}` is global too (rule 65). `GET /api/patterns` answers `{thresholds, patterns[{...pattern, qualifies, cost}] sorted by downtime cost, qualifying}`; `DELETE /api/patterns` empties the store. The mock plays `pattern` events in the tournament fixtures and serves the same endpoint. Plain (non tournament) waves are not mined yet.

### Implementation notes (TV3-C12 fix specs and lint)
- `.kiro/specs/hardening-<runId>/{requirements,design,tasks,README}.md`, written by `writeFixSpec` (packages/haunt/src/miner/specs.ts) for the qualifying patterns, sorted by downtime cost (lost orders and repeats break ties). `## R<n>. <signature>` has an EARS line (WHEN ... THE bot SHALL ...), `**Evidence:**` (run id and round, event seq, journal `path:line`, report link), `**Impact:**` (downtime, lost orders, repeats, points), `**Root-cause hypothesis:**` and `**Covered by lessons:**`. `### D<n>` has `**Patch:**`, `**Files:**`, `**Why:**`, `**Risk:**`, `**Rollback:**` and `**Diff budget:** under N lines.` (N at most 40; a pattern whose smallest patch is bigger, or with no known patch, is listed in the README under "Not proposed" and gets no requirement). `- [ ] T<n>` has `**Regression test:**` (a fast-check property or a fixture replay and its file) and `**Acceptance:**` (rerun the plan, expect the pattern gone and downtime under 5 s). The README has the table, the expected grade change, what lessons already cover and the lint command.
- `npm run haunt -- spec-lint <dir>` exits 1 when a requirement is not EARS, lacks evidence, impact or a hypothesis, has no patch (with a file, risk, rollback and a budget of at most 40 lines) or no task (with a regression test and an acceptance line), or when a task or patch says rewrite; 0 when clean, 2 for usage. MCP tool `haunt_specs {action: list|write|lint, run?, dir?}` lists qualifying patterns and spec folders, writes a spec for the `new` patterns (they become `suggested`) and lints a folder.
- `POST /api/specs {runId?}` writes a spec for the qualifying `new` patterns (409 `not_applicable` without a specs folder, 409 `not_ready` with nothing waiting), sets them `suggested`, emits `pattern` events for the change and `spec_written {runId, path, patterns[], refused[], lint {ok, issues[]}}`, and answers the same object. `GET /api/specs/<hardening-name>` answers the lint result. The server writes the spec by itself when a tournament ends if it has a specs folder (`npm run live` does). The reviewer (`runReviewer` with `fixSpec: true`, and `onWaveEnd` with `fixSpec`) uses the same writer; without the flag its rule-based text is unchanged. Nothing applies a spec: Kiro does, with the review step.

### Implementation notes (TV3-C13 improve loop)
- `POST /api/improve {seed?, rounds?, speed?, pace?}` answers `{improve: "imp-...", phase}` at once (400 on a bad plan, 409 `wave_running` while a wave or another improve run is going) and runs: 1. the plan (a tournament, lessons reset, the loop presses Next itself: it is the explicit auto-continue), 2. mine, 3. apply the cheap patterns as policy overlay (`accepted`) for tiers whose parts allow the action, 4. write a spec for the rest (`suggested`; `spec_written`), 5. rerun the same plan and seed (lessons kept), 6. compare. `GET /api/improve` follows it: `{id, phase: before|mining|applying|after|comparing|done|error, startedAt, request, report?, spec?, error?}`.
- `report`: `{closed, of, summary: "closed 7 of 9 patterns", grade {before, after}, reliability, score, lost, repeats (each {before, after}), closed, closedOnTreated, patterns[{id, signature, handling: overlay|spec|overlay+spec|nothing, before, after, status, closed, closedOnTreated, lanes {before[], treated[], after[]}}], overlays[{lane, tier, signature, action, stage, fault, existing}], spec {runId, path, patterns[], refused[], lint}|null, newPatterns[], runs {before, after}, text}`. A pattern is `verified` only if the rerun shows its signature gone; one the loop acted on that is still there is `applied`; a spec-only pattern that is still there stays `suggested`. Run reliability is orders done over orders given with each repeated effect costing half an order; the grade is `gradeFor` of that. `pattern` events carry the status changes.
- Lessons learned in a round already carry into the next one, so for a pattern the first run's own round-end learning covered, the loop reports the overlay as `existing: true`. All four actions change bot behaviour now, for the tiers whose parts allow them: `retry_backoff` (any transient failure of the stage, not only the fault the lesson was taught by; 5 attempts, exponential from 500 ms; also read by the transit poll and the handoff retry), `idempotency_key` (an effect of that stage sent without a key gets `<order>:<kind>`; needs `idempotency`), `journal_replay` (a stage the retries could not beat replays the order from the journal once after a 3 s cool-down instead of failing it; needs `journal`) and `breaker_park` (the breaker trips after two failed attempts instead of four so the order parks; needs `breaker` and `offline_queue`). `hold_and_reroute` is shown only. No code is applied: overlays are data, specs are documents (AGENTS.md).
- `npm run haunt -- improve [--url http://127.0.0.1:7070] [--seed N] [--rounds JSON] [--speed N] [--pace slow]` starts the job on a running server, prints the phases and the report, exits 0 when done, 1 on error, 2 when no server answers.

### Implementation notes (TV3-C9 curses)
- Wire kinds: `404` (Cursed 404: a seeded 15 to 40 percent of calls to the endpoint answer 404), `slow` (Slow Hand: every call takes 2 to 8 s more), `flaky500` (a share of calls answer 500), `clock_skew` (Skewed Clock: answers normally, the header `X-Haunt-Clock-Jump` and the server time jump), `rate_limit` (Rate Limited: a share of calls answer 429 with `Retry-After: 1`). A curse lies on one `endpoint` (the provider service: `account, order, charge, email, store, dispatch, notify, tracking, handoff`) of one lane, seeded per call so a replay lies the same way.
- `curse_start {id, kind, endpoint, rate?, delayMs?, source: "plan"|"player"}` and `curse_end {id}` are lane events (rule 66: valid kind, a `curse_end` ends a curse in force). They are published when the curse is added or ended, also between waves (stamped with the last wave number). Curses persist across waves and rounds until ended, also on a lane that was eliminated (a corpse keeps its tag); a new tournament clears them. `state.curses[] {id, lane, kind, endpoint, rate?, delayMs?, source?}` is rebuilt from the events; `GET /api/curses` answers `{curses[], table[], kinds[], endpoints[]}`.
- The plan: when a tournament round starts every live lane is topped up to the level's curses per lane (spec 5.1 table: none up to level 3, 1 at 4 to 6, 2 at 7 to 9, 3 at level 10, all five at 11), seeded, never the same kind twice on a lane. `POST /api/curse {lane 1..5, kind, endpoint}` curses a lane (400 `bad_lane` / `bad_request`, answers the curse); `POST /api/curse/end {lane, id}` ends one (404 if not in force).
- `curse_response {order, stage, curse, class, id?, endpoint?, status?}` (lane event, `order` and `stage` also on the envelope) is emitted once per (order, stage, curse) just before the order's `order_done`, `order_failed`, `order_parked` or `order_quarantined`. Class: `handled` (the step happened after all: a retry or fallback got through; for steps with no ledger row, the order finished), `reported` (the error surfaced and the order was parked or failed with an error), `swallowed` (the order finished but the step's ledger row never appeared: the error vanished and the step was skipped), `crashed` (the process died after the lie, or the order failed with no error shown). Swallowed and crashed count as an issue (floor rule, lap issues); a swallowed answer caps the order's review at two stars and its delivery sub-score at one.
- Report: `round_end.curseTable` and `tournament_end.curseTable` are "what each lane returned when the API lied": `[{lane, tier, curse, endpoint, handled, reported, swallowed, crashed, total, verdict}]`. The Casebook and the miner read the answers as cases with signature `stage + curse_<kind> + <class>` (handled is solved by `retry`, reported is partly, swallowed and crashed are lost).
- Fixture `curses-404`: a Cursed 404 on the charge endpoint of lanes 1 to 4; the Rookie reports and crashes, the Retrier and Reconciler handle it, the Journaler swallows one. The mock serves `POST /api/curse`, `GET /api/curses` and `state.curses`.

### Implementation notes (TV3-C3, C4, C5)
- `intensity {level, source, autoRamp?}` is a global event (no `lane`; `wave` is present only when a wave has started). `state.intensity = {level, autoRamp, everyN, max}`, default `{level: 3, autoRamp: false, everyN: 4, max: 11}`. `POST /api/intensity {level 1..11, autoRamp?, everyN?, max?}` answers the new `state.intensity`; a bad level or flag is `400 bad_request`. The server emits `intensity {source: "player"}`; auto-ramp emits `{source: "ramp", autoRamp: true}` each time it raises the level (one level per `everyN` finished orders, counted once per order id across lanes). `source: "plan"` is reserved for fixtures. Rule 56: `intensity.level` is an integer from 1 to 11.
- The dial scales the random plan (chaos mode `random`) live, from the next tick on, so orders not yet started feel it. Until the dial has been set once, the older `frequency` plan runs unchanged. `endpoint_down` and the service-down outage lengths follow the level from the start (default 3).
- `outage` carries the length in `detail`: `{outageMs, seed, fault, level}` (1x ms, so the real window is `outageMs / speed`) and the stage on the envelope. It is emitted right after the `chaos` event of the press. A press that fixes its window (`forMs`, a boss, a sweep, a fuzz window) has no `outage` event. The lap recovery time is the drawn window plus recovery work because the provider really is down for that long.
- Unknown faults: the `chaos` event adds `unknown: true`, `fingerprint: "fz-xxxxxxxx"`, `source: "fuzz"` and `fuzz: {fault, status?, forMs?, count?, truncated?, clockJumpMs?}`; `fault` is the known fault the shape is built on, `creature` is that fault's creature. The fingerprint is a hash of the shape, so the same shape has the same id.
- Gremlin: `chaos` with `fault: "gremlin"`, `creature: "gremlin"`, `source: "gremlin"` and `variant` (`slow_link`, `http_500` or `duplicate_request`, each with a call count of one). The scheduler injects it for a lane that has had no issue by the middle of the expected round, in every chaos mode. An issue is a `stage_fail`, `process_dead`, `repeat`, `order_parked`, `lane_halted`, an opened `breaker`, or the gremlin itself.
- `wave_end.summary[lane].issues` is the lane's issue count (live: from the lap tracker, the order in flight included; mock fixtures built with the floor option carry it too). A lane with zero issues also gets `floorOk: false` (the engine assertion, P19). The `calm` fixture stays calm: the floor is an option of the mock planner, on for `intensity-11`-style fixtures and tests.
- `review` input gains `gremlin`; with a gremlin and more than one second of normalised downtime the stars are capped at 4.5.
- Fixture `intensity-11` is in the mock: five lanes, the dial at 3 then 11, a fault on every effect stage of every order, unknown faults with fingerprints and drawn outages.
