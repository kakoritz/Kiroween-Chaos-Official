# Contract v1.1 (additive)

Adds the play-test v2 features (`.kiro/specs/playtest-v2/`). **Everything here is additive**: `contractVersion` stays `1`, and `hello` gains `contractMinor: 1`. Clients ignore unknown fields and event types, so v1.0 clients keep working. Where this file differs from `PROTOCOL.md`, **this file wins**. Rules continue the numbering of `PROTOCOL.md` (rules 40 and up).

## 1. Pace and travel

- `pace` accepts `normal` (factor 1), `show` (factor 2), `slow` (factor 3). `wave_start.detail.pace` echoes it. **`slow` is the default** for interactive play and demo scripts. Fixtures use `show` unless a fixture says otherwise.
- All travel and ceremony times below are base values at 1x, multiplied by the pace factor and divided by `speed`. Events carry **real ms**.

| Constant | Base (1x) | Meaning |
|---|---|---|
| `walkMs` | 400 | skeleton walks from one station to the next |
| `grabMs` | 500 | skeleton grabs the scroll at the start of the track |
| `ceremonyMs` | 1600 | handoff door ceremony (door opens, scroll handed over, stars float, door closes) |
| `returnMs` | 1800 | skeleton runs from the door back to the start of the track |
| `cancelMs` | 900 | cancelled-order sequence (scroll burns, slump) before the return |

### Guarantees (rule 40)
1. `stage_done.detail.walkMs` (absent on the last stage and on skipped replay pairs): the lane's **next `stage_start` is emitted no earlier than `walkMs` after this `stage_done`.**
2. `order_start.detail.grabMs`: the **first `stage_start` of that order is emitted no earlier than `grabMs` after `order_start`.**
3. `order_done.detail.ceremonyMs` and `returnMs`: the lane's **next `order_start` is emitted no earlier than `ceremonyMs + returnMs` after `order_done`.**
4. `order_failed.detail.cancelMs` and `returnMs`: the next `order_start` is no earlier than `cancelMs + returnMs` after `order_failed`.
5. Process restarts, replay pairs, retries, parking and resume are exempt from walk (0 ms). After a restart the skeleton reappears at the station of the open stage (or at the start for a no-memory bot).
The server enforces these gaps by waiting. The UI animates inside them and never delays or reorders events.

## 2. Handoff is a provider call (engine change, UI-visible)

Stage 8 `handoff` makes one provider call `GET /handoff/:shipment?lane=` returning `{status:"delivered"}` normally. It is a **poll-role** call: faults can make it return `no_answer`, `gated`, `accident` or `wrong_order` for a window. Retry rules are the same as for `tracking` (engine design sections 4 and 7). Stage role in `haunt.yaml`: `poll` with `final: true`.

## 3. Lap object (rule 41)

`order_done`, `order_failed` carry `detail.lap`:
```
lap: { ms, workMs, attempts, retries, downtimeMs, issues: [{stage, count}],
       recoveries: [{stage, action, ms}] }
```
- `ms`: from `order_start` to the order's last event (`order_done`/`order_failed`), **including grab and walks, excluding ceremony and return**.
- `workMs`: `ms` minus grab and walks.
- `attempts`: number of `stage_start` plus in-stage call attempts (every `stage_fail` counts one extra attempt) for this order.
- `retries`: number of `recover_start` with action `retry`, `backoff` or `restart`, plus resumes after a park.
- `downtimeMs`: union of downtime intervals (engine design section 3 of playtest-v2), **real ms**.
- `issues`: per stage count of **issue events** (below). Stages with zero issues are omitted.
- `recoveries`: one entry per finished recovery interval with its action and real ms.

### Issue events (the one definition, used by server and UI)
An **issue** at a stage is any of: `stage_fail` (including `degraded`), `process_dead` while that stage is open, `repeat` caused at that stage, `breaker{open}` while that stage is waiting, `order_parked` at that stage, `chaos_absorbed` does **not** count. The chip flag counts issue events for the current order at that stage.

## 4. Review event (rule 42)

`review` (lane-level), emitted **immediately after `order_done` or `order_failed`** and before the next `order_start`:
```
review: { order, stars, sub: {timeliness, delays, issues, delivery, ease},
          reasons: [string], text, cum: {stars, max, count} }
```
- `stars` and each `sub` value are numbers in 0.5 steps from 1 to 5. A cancelled order has `stars: 1`.
- `cum` is the running total for the lane in this wave: `stars` is the sum of all stars so far, `max` is `5 x count`, `count` is orders reviewed. The tracker shows `cum.stars/cum.max` (5/5, then 6/10, then 8/15).
- No review for `quarantined`, `parked` (until resolved) or `abandoned` orders.
- Formula and reason templates: `playtest-v2/design.md` section 6.

## 5. Score reasons added

`downtime`, `review`, `order cancelled`, `order abandoned`, `boss recovered`, `boss downtime refund`, `refund`, `discount`. Existing reasons are unchanged. Amounts: `playtest-v2/design.md` section 5. `order failed` is replaced by `order cancelled`.

## 6. Wave summary additions (rule 43)

`wave_end.detail.summary[lane]` gains:
```
orders: {done, cancelled, parked, quarantined, abandoned},
bestMs, slowestMs, avgMs, totalMs, retries, downtimeMs,
issuesByStage: {stage: count},
stars: {sum, max, count, avg}, rating?: "Five-Star Crypt"|"Respectable"|"Spooky Service"|"Cursed"
```
`rating` from avg stars: 4.5 or more Five-Star Crypt, 3.5 or more Respectable, 2.5 or more Spooky Service, else Cursed. `rating` is absent when `stars.count` is 0 (a lane with no reviews has no rating, not Cursed); consumers must treat a missing `rating` as unrated. `bestMs` and `slowestMs` are lap `ms` of completed (`done`) orders; absent if none.

## 7. Decisions (wrong-order mechanic, rule 44)

- `decision_needed` (lane-level): `{order, kind: "wrong_order", detectedAt: "confirmation"|"handoff", options: ["refund","discount","redo"], defaultChoice, timeoutMs}`. `timeoutMs` is real ms.
- `decision_made`: `{order, choice, source: "user"|"default"|"timeout"}`.
- `POST /api/decision {lane, order, choice}` returns `200 {}` or `409 {error:{code:"no_decision"}}`.
- Order of events: `chaos{fault:order_typo}`, then at detection `stage_fail{error:"wrong_order", retryable:false}`, then `decision_needed`, then `decision_made`, then the resolution:
  - `refund`: `effect{kind:"refund"}`, then `order_failed{outcome:"cancelled", reason:"refunded"}`, `review`.
  - `discount`: `effect{kind:"discount"}`, then the order continues to `order_done` (with `lap.issues`), `review`.
  - `redo`: `effect{kind:"refund"}` for the wrong charge, then `order_start{redo:true, index same}`; chips reset; a corrected order runs from intake with new keys (`<order>:charge:r1`).
- Effect kinds added: `refund`, `discount`. The ledger exemption: an extra `charge` row whose key ends in `:rN` after a `refund` row is **not** a repeat.

## 9. State and endpoints

- `GET /api/state` lane objects add: `stars: {sum, max, count}`, `lap: {orderIndex, ms, issues: [{stage,count}], downtimeMs}` (the lap so far), `decisionPending: {order, options, timeoutMs, expiresAt}` or `null`.
- `GET /api/lane/:lane/order/:order` returns the order record: `{order, outcome, startTs, endTs, lap, review, stages: [{stage, status, attempts, retries, recoverable, issues, downtimeMs, ms, recoveries: [{startTs,endTs,ms,action,depth}]}]}`. `recoverable` is true if a failure at that stage was followed by a successful stage.
- `GET /api/lane/:lane/laps` returns `[{order, outcome, lap, review}]` for the current wave.
- `GET /api/waves/:n/laps` returns `{lanes: [{lane, tier, laps: [...]}]}`. `GET /api/waves/:n/stars` returns `{lanes: [{lane, series: [{order, stars, cumStars, cumMax}]}]}`.
- `POST /api/wave/start` accepts `pace: "slow"` and `lanes`, `orders` as before.
- `inpage` transport mirrors these as `getLaneOrder(lane, order)`, `getLaneLaps(lane)`, `getWaveLaps(n)`, `getWaveStars(n)`, `decide(lane, order, choice)`.

## 10. Ordering rules (continued)

40. The travel guarantees of section 1.
41. `lap` is present on every `order_done` and `order_failed`.
42. `review` follows `order_done`/`order_failed` directly (no other event of that lane in between) and precedes the next `order_start`. `cum` is monotone: `count` rises by 1 per review.
43. `wave_end` summary fields of section 6 are present for every lane.
44. A `decision_needed` is followed by exactly one `decision_made` for the same order before any other `stage_start` of that lane.
45. `score{reason:"downtime"}` is emitted at the **end of each recovery interval** (when the stage finally completes) with a negative `delta`; at most one per interval.
46. `score{reason:"boss recovered"}` and `score{reason:"boss downtime refund"}` are emitted together when the in-flight order of the boss hit completes.
47. `chaos` events for the new world faults carry `creature` from section 8 and `fault` from section 8.

## 12. Campaign: GET /api/campaign (additive, CP-C1)

`GET /api/campaign` (mock and live) returns `{nights: CampaignNight[], gear: CampaignGear[], start: {gear: string[], credits: number}}`. Data source: `packages/core/campaign/nights.json` and `gear.json`; schema `packages/core/campaign/nights.schema.json`; TypeScript types `packages/haunt/src/campaign/types.ts`. `inpage` mirrors it as `getCampaign()`.

```
CampaignNight = {
  id: 1..7 (7 is the finale), title, briefing, lesson: [3 lines], hint,
  orders: 4, pace: "slow", seed: int (fixed, so a night is deterministic),
  app?: "orders"|"inbox", finale?: true,
  plan: [ demo-script press | {boss, warnAtMs, startAtMs} ],      // lane 1 triggers, runtime.md section 33
  rivals: ["retrier","journaler","reconciler","phoenix"],
  medals: { bronze:{credits}, silver:{credits,repeats}, gold:{credits,repeats,avgStars?,cancelled?,abandoned?,maxDowntimeMsPerOrder?} },
  gearHint: PartId[]
}
CampaignGear = { id, label, badge: "R"|"J"|"I"|"B"|"Q", part: PartId, cost, effect, blocks }
```

Medal rule (pure, `packages/haunt/src/campaign/medals.ts`): the medal is the highest tier whose thresholds are all met by `wave_end.detail.summary[1]`. `credits` is a minimum lane score, `repeats` a maximum, `avgStars` a minimum, `cancelled` and `abandoned` maxima, `maxDowntimeMsPerOrder` a maximum for `downtimeMs` divided by the order count. Credits awarded: `max(0, score)` the first time a tier is reached for that night, 25 percent (rounded down) on replays.

Nothing else changes: existing fields and endpoints are untouched.

### Starting a night (additive, CP-C2)

`POST /api/wave/start` accepts `campaign: {night: 1..7, parts?: PartId[]}`. The night fixes `orders`, `seed`, `pace` (`slow`), `lanes` (5), `tiers` (`race`) and `app` (night 6 is `inbox`); those request fields are ignored. Lane 1 runs as the **Crew bot** with exactly `parts` (unique, canonical order), lanes 2 to 5 are the rival tiers (retrier, journaler, reconciler, phoenix). A bad night or part gives `400 bad_request`. `wave_start.detail` gains an optional `campaign: {night, parts}`. `lane_ready` for lane 1 is `{tier: "crew", label: "Your Crew", parts}`; the `tier` enum of `lane_ready` gains `crew`. The Crew bot reads `HAUNT_PARTS` (ids or gear letters R J I B Q) and sends idempotency keys only when `idempotency` is in the list. The night's `plan` is played against lane 1 as a demo script (`packages/haunt/src/campaign/wave-config.ts`).
